## 执行顺序

1. **审计与规划**：核查 PI Bot 与 PI Desktop 接口；建立现有能力清单、边界和测试基线。
2. **首轮可靠性接入**：优先修复现有 `message_bot` 的持久去重、崩溃窗口和可观察状态；复用现有任务队列和单写入口，不新建并行消息系统。具体改动以审计为准。
3. **任务依赖与验收**：在现有 jobs/reports 上渐进增加依赖验证、确定性验收证据及明确的恢复语义。完成首批可靠性补丁的真实宿主测试后再接入。
4. **执行效率**：能力匹配、预算告警、可选工作目录与文件协作约束。目录分开不等于安全隔离；调用后统计不等于实时硬预算。
5. **产品与发布**：使用现有任务/恢复 UI 展示简洁状态，递增候选包版本并本地校验；完成真宿主与旧数据回归后再公开发布。

## 投入顺序与取舍

| 批次 | 范围 | 收益与成本 | 放行条件 |
| --- | --- | --- | --- |
| 1A 本轮已做 | 请求/任务接收确认、失败回滚、重启核对、有界事件、状态查询 | 直接处理现有派发不确定窗口；不增加模型回合，不引入新依赖 | 原有测试及故障注入通过；包内校验通过；公开发布仍需真宿主验证 |
| 1B 下一批 | 先统一新旧派发与恢复入口的持久准入，再考虑回执保留策略 | 覆盖尚未纳入事务的 planner/旧工具等入口；风险中等，需要逐入口测试 | 避免旧调用语义、自动回交、群内流式呈现和权限行为倒退 |
| 2A | 现有计划中的依赖任务与独立验收证据 | 比继续堆新 Bot 更有助于真正完成任务；成本中高 | 拒绝环、依赖失败不解锁、失败验收不报完成；确认外部验证权限 |
| 2B | 能力匹配、工作区成果索引、可控恢复 | 复用已有能力库/记忆/用量；不新建平行系统 | 真任务对照额外调用和耗时；未知副作用不自动重做 |
| 后续按测量决定 | 临时 Agent、预算限制、可视化看板、可选文件协作约束 | 有需求才加；不以功能数量判断价值 | 证明增加的复杂度、成本和故障面小于实际收益 |

不增加独立运行框架、独立浏览器、云中继、Docker 或新数据库。优先复用现有结构，避免额外部署和兼容成本。

## 真实宿主验收清单（待运行）

先导出完整备份，在 PI Desktop 导入候选包，记录实际宿主版本与模型。不能用仓库最新 SDK 替代本机接口结果。

1. 普通私聊/新群打招呼：管理员与执行者继续边生成边显示；记录首字延迟和最终全文一致性。新增可靠性机制不得强制加入一次模型规划/审核调用。
2. Agent 以稳定 request_id 连续两次派发同一任务：只产生一个执行者任务；结束回合后自动接回结果；改内容复用编号应拒绝。
3. 执行者尚未启动时关闭/重启宿主：恢复中心可核对中断任务；不得静默重发原生提示或有副作用工具。
4. 原生权限为询问时触发需要审批的动作：仍展示宿主审批，不自动接受、不添加权限。
5. 备份→删除 Bot→重启→恢复备份：分别验证删除持久性、主动恢复语义、头像与记忆正常；已停止任务不自动重新执行。
6. 语音、附件/粘贴、侧问、群管理员派发、结果回交正常；工作目录与操作系统差异仍按现有宿主能力判断。

本文件保留阶段规划与待验收项目；首批改动随 0.3.89 合并发布，真实宿主验收仍按本清单记录。
